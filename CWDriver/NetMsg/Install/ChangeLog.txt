Version 1.1.1619 R 1.8.2012
- BUG: #276, 'server send' and 'client send' commands could access just having
       disconnected client, what could cause driver crash.

Version 1.1.1532 R 4.9.2011
- BUG: #248.1, disconnect notification could be processed after client deallocation
       (client leave). Code was changed to use different client-alive detection.
       #248.2, when disconnected, new connection was sometimes impossible. The
       connection did not clean up owned resources completely, so new connect
       thought that something is still pending. Not tested in original environment.

Version 1.1.752.N/R 5.3.2009
- BUG: #50, driver's OnReceive was called sonner than OnConnect. Driver had not
       built client structures and it crashed during received data processing.
- BUG: Closed client connection notified server with two notifications. There was
       race condition between these notifications, the second one could access NIL
       pointer.
- BUG: Client which connects/sends/disconnects fast could cause assertion in server.
       Server started reading asynchronously, which could be done after disconnecting,
       out of order. Now data are received in order. The bug could also lead to
       ignoring requests from such fast clients.
- BUG: If connection was dropped just during accept processing driver could
       stop in ASSERT due to unexpected state.

Version DEBUG 1.1.1490 24.3.2008
- BUG: r1443-5, for multiprocessor machines receive and send queues can be left
       in incoherent state. Until there appeared new explicit send or receive request
       nothing was transferred. For driver, where read operations are automatic,
       it could lead to stop of receiving (until peer side sent something).
- BUG: r1452, r1489, CW2000 did not work with the driver, there was missing support
       for CW2K strings for both set and get operations
- BUG: r1419, r1430, receive queue could have get full without signalizing reader.
       For driver it could cause indefinite stop of receiving.
- BUG: r1377, internal network handler could have been used for socket notifications
       before it was fully prepared. This could have resulted to silent no-functional
       behavior from driver start.

Version 1.0.963 beta 26.8.2007
- BUG: client could leave some unread data in buffer after disconnect. Next reading,
       after reestablishing the connection, then got from the buffer bad data.
       The buffer is cleared now.
- BUG: if peer side ended connection inside socket receive loop, the socket
       remained in infinite loop (recv returned 0).
- BUG: server could send data to client after removing the connection, request to
       send was queued sooner than disconnect notification. Server found this,
       but it did not recover and it could damage the memory or access unnalocated
       memory.
- BUG: when network data came across the buffer boundary, it was possible that
       not completed buffer filling did not wait for data, but started new buffer
       reading. Data could be received corrupted.
